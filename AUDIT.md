### Многопроцессность: отрицательный результат

Пользователь просил загрузить процессор сильнее. Сделано разложение корня по
процессам (`engine/parallel.py`), по дороге найдены и исправлены две
собственные ошибки: несбалансированное разбиение (лучший ход одному процессу,
все остальные тридцать — второму) и сравнение оценок процессов, дошедших до
**разной** глубины.

Но даже после этого **прироста силы не видно**. Матч 2 процесса против 1 при
1.5 с/ход, 10 партий:

```
ИТОГ 10 партий: 2 процесса 4.5 - 5.5 1 процесс
```

То есть 45% — статистически это **неотличимо от равенства**: при n=10
доверительный интервал порядка ±300 Elo, и такой результат одинаково
согласуется и с «чуть хуже», и с «чуть лучше». Утверждать, что параллельный
поиск проигрывает, на этих данных нельзя. Можно утверждать другое, и этого
достаточно для решения: **выигрыша он не показывает, а процессорного времени
съедает вдвое больше.**

Причины, почему выигрыша и не ожидается, структурные:

* процессы не делят таблицу транспозиций — каждый считает своё;
* родитель может сравнивать их только на глубине, которую успел **самый
  медленный**;
* предпоиск для упорядочивания корня съедает часть бюджета;
* без общей alpha процессы не отсекают друг за друга, и суммарно узлов
  просматривается втрое больше при той же глубине.

Настройка оставлена (1–4), но **по умолчанию 1**, и в интерфейсе она помечена
как экспериментальная с этим же результатом. Загрузка CPU вырастет, сила — нет.

Чтобы многоядерность реально заработала, нужна **общая таблица транспозиций в
разделяемой памяти** (`multiprocessing.shared_memory` + плоский массив
фиксированных записей). Это отдельная задача: `Manager`-словарь не подойдёт,
одно обращение к нему дороже, чем вся оценка позиции.

## 2. Критические дефекты

### C1 — Таблицы PST применяются вверх ногами. Для обоих цветов.

`recovered_src/engine/evaluation.py:217-228`

```python
for sq in board.pieces(piece_type, chess.WHITE):
    mg_score += PIECE_VALUES[piece_type] + PST_MG[piece_type][sq]      # ← сырой sq
for sq in board.pieces(piece_type, chess.BLACK):
    msq = _mirror_square(sq)                                            # ← зеркало
    mg_score -= PIECE_VALUES[piece_type] + PST_MG[piece_type][msq]
```

Все таблицы записаны «визуально»: первая строка литерала — 8-я горизонталь,
последняя — 1-я. Это видно по содержанию однозначно:
* `PAWN_PST_MG` последняя строка — нули (на 1-й горизонтали пешек не бывает),
  предпоследняя `5,10,10,-20,-20,10,10,5` — штраф за неразвитые d2/e2;
* `KING_PST_MG` последняя строка `20,30,10,0,0,10,30,20` — бонус за рокировку на 1-й.

В python-chess `A1=0 … H8=63`. Значит для **белых** нужен `sq ^ 56`, а для чёрных —
сырой `sq`. В коде ровно наоборот. **Вертикальное зеркало применено к обеим сторонам.**

**[проверено]** Замеры текущего поведения:

| Позиция | PST_MG | PST_EG |
|---|---|---|
| Белая пешка e2 (стартовая) | **+50** | **+80** |
| Белая пешка e4 | +25 | +30 |
| Белая пешка e7 (шаг до ферзя) | **−20** | **+10** |
| Белый король e1 | **−50** | |
| Белый король g1 (после рокировки) | −40 | |
| Белый король g8 (в лагере противника) | **+30** | |
| Белая ладья на своей 2-й горизонтали | **+10** | |
| Белая ладья на 7-й горизонтали | **−5** | |

Сквозные оценки позиций **[проверено]**:

| | сейчас | после исправления |
|---|---|---|
| K+P на d2 vs k | +148 | +78 |
| K+P на d5 vs k | +123 | +133 |
| K+P на d7 vs k (шаг до ферзя) | **+168** | **+238** |
| K+R: король на e1, ладья h1 | +550 | +550 |
| K+R: рокирован g1, ладья f1 | **+538** | **+558** |

То есть продвижение пешки с d2 до d7 движок сейчас оценивает в **+20 сп**
(реально ≈ +160), а рокировка стоит **−12 сп** вместо +8.

Ущерб по фигурам, от большего к меньшему:
* **Пешки — катастрофа.** MG-таблица платит +50 за пешку на месте и −20 за пешку
  на 7-й. EG-таблица: +80 за пешку на 2-й, +10 за пешку на 7-й. Проходную спасает
  только `PASSED_PAWN_BONUS` (он индексируется по рангу и корректен), но его
  выигрыш почти целиком съедается PST.
* **Король в миттельшпиле — тяжело.** e1 = −50, g8 = +30. Таблица активно
  поощряет марш короля вперёд и почти не платит за рокировку.
* **Ладьи — заметно.** Бонус «+10 за 7-ю горизонталь» достаётся ладье на своей
  второй. Идеи «ладья на 7-й» у движка нет вообще.
* Слоны — мелочь (≤10 сп, любит Bg5/Bh6, недооценивает Bc4/Bd3).
* Кони и ферзь — почти без разницы, их таблицы вертикально симметричны.

**Исправление:** поменять местами — белые через `_mirror_square(sq)`, чёрные через `sq`.

> Важно: оценка при этом остаётся **строго антисимметричной по цвету**
> (**[проверено]**: 0 из 4 тестовых позиций дали расхождение с зеркалом).
> Ошибка бьёт по обоим цветам одинаково, поэтому она не проявляется как
> «движок играет за белых лучше, чем за чёрных» — она проявляется как
> «движок не понимает пешки, короля и ладьи».

### C2 — Шах продлевает поиск дважды. Дерево растёт вглубь без ограничения.

`recovered_src/engine/search.py:320-323` и `search.py:381-384`

```python
# у родителя, ПОСЛЕ board.push(move):
gives_check = board.is_check()
if gives_check:
    extension = 1                       # → потомок вызывается с depth-1+1 = depth
...
# у потомка, в начале _negamax:
is_in_check = board.is_check()
if is_in_check:
    depth += 1                          # → depth+1
```

Один и тот же шах засчитывается два раза: один раз родителем как «мой ход даёт шах»,
второй раз потомком как «я под шахом». Итог: **каждый шах не сохраняет остаточную
глубину, а увеличивает её на 1.** По цепочке шахов глубина растёт неограниченно.

**[проверено]** Инструментированный `_negamax` с корневой глубиной **4**
доходит до **ply 102**.

Последствия — измеренные, не гипотетические:

| Позиция | Время | Глубина | Мат найден |
|---|---|---|---|
| KQ vs K | 8 с | **1** | **нет** |
| KRR vs K (мат в ≤5) | 6 с | **1** | **нет** |
| KR vs K | 8 с | 6 | нет |
| Итальянская партия | 5 с | 4 | — |

**Движок не в состоянии поставить мат ферзём и королём.** В KQ vs K он за 8 секунд
не заканчивает даже вторую итерацию.

+        if is_in_check:

### C4 — Quiescence не видит мат и «пасует», находясь под шахом

`recovered_src/engine/search.py:257-310`

```python
stand_pat = evaluate(board)
if stand_pat >= beta:
    return beta
```

`evaluate()` (`evaluation.py:478-495`) знает только про пат и недостаток материала.
Мата в ней нет. Значит `stand_pat` в заматованной позиции — обычная материальная оценка.

**[проверено]** Позиция после `Ra8#`: `is_checkmate=True`, `evaluate() = −24`,
`_quiescence(qs_depth=1)` возвращает **−24** вместо ≈ −99999.

Основной поиск от этого частично защищён: `depth += 1` при шахе (`search.py:322`)
не даёт узлу под шахом провалиться в qsearch. Но **qsearch рекурсирует сам в себя**,
не возвращаясь в `_negamax`. Любой шах, данный внутри qsearch, приводит в узел,
где сторона под шахом спокойно «стоит на месте» и возвращает статическую оценку.

Два следствия:
* маты и материальные потери на горизонте невидимы;
* сторона под шахом получает бесплатную опцию «ничего не делать», то есть
  преимущество атакующего систематически занижается.

Плюс: ветка `qs_depth == 0` (`search.py:273-285`) генерирует **все шахующие ходы**
через `push` / `is_check` / `pop` для каждого легального хода — и делает это
в **каждом листе основного поиска**. В KQ vs K, где почти любой ход — шах,
именно это добивает скорость.

## 3. Высокая важность

### H1 — SEE считает неправильно и меняет знак на частых взятиях

`search.py:81-103`. Последний член формулы не имеет смысла:

```python
return victim_val - attacker_val + min(attacker_val, min_defender_val)
```

**[проверено]**:

| Взятие | SEE движка | Правильно | |
|---|---|---|---|
| RxB, слон не защищён | +330 | +330 | ок |
| **RxB, слон защищён ферзём** | **+330** | **−170** | **смена знака** |
| **QxR, ладья защищена ладьёй** | **+100** | **−400** | **смена знака** |
| QxP, пешка защищена пешкой | −700 | −800 | знак верный |
| **Взятие на проходе** | **0** | +100 | жертва не найдена |

На взятии на проходе `board.piece_at(to_sq)` пусто, поэтому `victim is None` → 0.
Размен глубже одного полухода не считается, батареи и рентген не учитываются,
превращения с взятием не обрабатываются.

Где бьёт: `_order_moves:231-236` кладёт заведомо проигрышные взятия в корзину
«выигрышных» (`1000000 + mvv_lva`), а в qsearch отсечка `see < 0` (`search.py:299`)
на них не срабатывает. Итог — испорченная сортировка и, как следствие,
меньше отсечек и меньше реальной глубины.

### H2 — Contempt имеет неверную чётность

`search.py:254-255`, используется в `:318` и `:367`.

```python
def _contempt_draw_score(self) -> int:
    return -CONTEMPT          # −30 от лица стороны, которая ходит, на ЛЮБОМ ply
```

В negamax это значит: ничья на чётном ply (ходит движок) = −30 — правильно,
движок её избегает. Ничья на **нечётном** ply = −30 для соперника = **+30 для движка**.

**Любая линия, в которой ничью может форсировать соперник, читается движком
как +0.30 в свою пользу.** Он будет целенаправленно идти в такие линии вместо
любых, которые оценивает ниже +0.30. Это классическая причина «бот сам загоняет
выигранную партию в повторение».

То же самое применяется к пату (`search.py:367`). **[проверено]** `_negamax`
на патовом узле возвращает **−30**, а не 0.

**Исправление:** знак contempt должен зависеть от цвета корня, а не от стороны,
которая ходит.

### H3 — Singular extension: неверный знак, неверный набор ходов, порча TT

`search.py:385-393`

```python
board.pop()
reduced_beta = tt_entry[1] - 30
singular_score = -self._negamax(board, (depth - 1) // 2, reduced_beta - 1, reduced_beta, ply + 1)
board.push(move)
```

Три независимые ошибки:

1. **Не исключён проверяемый ход.** Смысл singular-теста — «а хороши ли ОСТАЛЬНЫЕ
   ходы?». Здесь после `pop()` ищется та же позиция, где `tt_move` по-прежнему доступен.
   Тест бессмысленен по построению.
2. **Неверный знак.** После `board.pop()` ходит *наша* сторона, а результат
   отрицается. Получается `singular_score ≈ −tt_score`, и сравнивается это
   с `tt_score − 30`. Условие срабатывает всегда, когда `tt_score` больше примерно
   −15, и не срабатывает никогда в остальных случаях. Фактически это
   «продлевать TT-ход, когда мы не проигрываем» — случайное продление.
3. **Порча TT.** Проверочный поиск сохраняет запись **под ключом текущего же узла**
   на глубине `(depth-1)//2` и с `ply + 1` — то есть с неверной поправкой на
   расстояние до мата и с границей, полученной из перевёрнутого окна.

Плюс это стоит половинного поиска на каждом узле с `depth >= 6` и TT-ходом — впустую.

### H4 — Delta pruning с плоским запасом 200 сп

`search.py:265-266`

```python
if stand_pat + DELTA_MARGIN < alpha and qs_depth > 0:
    return alpha
```

`DELTA_MARGIN = 200`, а ферзь стоит 900. Нужно `stand_pat + самая_крупная_жертва + запас`.

**[проверено]** При `stand_pat = −19` и `alpha = +381` узел вернул `alpha`
(то есть отсёкся), несмотря на доступное взятие ферзя. Это ложный fail-low,
который прячет выигрыш ферзя.

### H5 — Futility pruning не умеет пропускать шахи и пишет TT_EXACT

`search.py:355-378` и `search.py:445-452`

```python
if futility_prune and i > 0 and not is_capture and not is_promotion:
    continue                      # решение принимается ДО board.push()
```

Так как `push()` ещё не сделан, неизвестно, даёт ли ход шах. При `depth <= 3`
и `static_eval + margin <= alpha` выбрасываются **все тихие ходы кроме первого** —
включая тихие матующие. Это ровно тот паттерн, при котором движок, отдавший
материал за атаку, не находит тихий матовый ход: `static_eval` низкий,
`alpha` выше, отсечка включается.

Второе: после выбрасывания большей части списка флаг всё равно выбирается по
`best_score` относительно `original_alpha`/`beta`. Узел с неполным списком ходов
может быть записан как **`TT_EXACT`** и позже использован как жёсткая отсечка.
Плюс отсечка не отключена на PV-узлах.

### H6 — History никогда не масштабируется; killers/history не сбрасываются

`search.py:442-443`:

```python
if self.history[0][0][0] > 50000:
    self._scale_history()
```

Проверяется ячейка `a1 → a1`. Такого хода не существует, значение всегда 0.
**`_scale_history()` — мёртвый код.** **[проверено]**: сама функция работает,
её просто никогда не вызывают.

При этом `history` и `killer_moves` не очищаются между ходами (`search()` их не
трогает; `clear_cache()` GUI намеренно перестал вызывать — см. комментарии
`main_window.py:335` и `:362`). History растёт на `depth²` за отсечку.
В длинной сессии анализа значения переползают полосу killers (800 000 / 900 000),
а затем и полосу взятий (1 000 000) — и порядок ходов инвертируется.

### H7 — Часы опрашиваются примерно раз в секунду

`search.py:259-261` и `:314-316`

```python

    if self._check_time():
```

4096 узлов при измеренных **4 000 узлов/с** — это **≈ 1.0 с между проверками часов**.
Движок бежит «вслепую» почти секунду.

**[проверено]** Перерасход бюджета: 5.98 с при лимите 5.00 с; 8.3 с при 8.0 с;

**Исправление:** маска `1023` (или `255`) — накладные расходы на `time.time()`

### M2 — `evaluate()` — потолок пропускной способности

**[проверено]** 156.6 мкс на вызов → ≈ 6 400 оценок/с. Разбор:

|---|---|---|

* `_evaluate_king_safety` (`evaluation.py:392-453`) пересобирает множества

`evaluation.py:359-369`. `board.attacks(sq)` — псевдоатаки: поля под своими

### M4 — Таблица транспозиций может занять ~800 МБ

`search.py:115`: `max_size = 2_000_000` на бакет, бакетов два. Запись — питоновский
tuple плюс объект `chess.Move` плюс слот словаря, порядка 200+ байт.

### M5 — Null-move выполняется раньше, чем определяется пат *(латентно)*

Порядок в `_negamax`: повторение → TT → `depth<=0` → **null-move** → futility →
генерация ходов → `if not legal_moves`. Патовый узел с `depth >= 3` и любой
не-пешечной фигурой до проверки на пат не доходит; отсечка `null_score >= beta`
вернула бы выигрышную границу для ничейной позиции.

Честно: **воспроизвести не удалось** — на моей тестовой позиции узел вернул
contempt (нулевое окно не дало отсечки). Помечаю как латентную дыру по чтению кода,
а не как подтверждённый дефект.

### M6 — TT отдаёт `alpha`/`beta` вместо самого счёта

`search.py:330-336`. На корне это значит, что `best_score` становится границей
aspiration-окна, а не оценкой, и `prev_score` для следующей итерации строится на ней.

### M7 — MultiPV не является MultiPV

`search.py:426-429` и `:538-546`. Записываются только ходы, получившие полное окно,
то есть только те, что подняли alpha. `root_moves_scores` очищается **раз на итерацию
глубины, но не на каждый повторный aspiration-поиск** (`search.py:482` вне `while True`),
поэтому счета провалившейся попытки смешиваются с финальной. `sorted_moves[:2]` —
жёстко зашитые 2 линии. Настоящий MultiPV требует цикла по корню с исключением
уже найденных ходов.

## 6. Что работает правильно

Это важно не меньше списка дефектов — здесь копать не надо:

* **Антисимметрия оценки по цвету точная** — **[проверено]** 0 расхождений из 4.
  Ошибка C1 бьёт по обоим цветам одинаково.
* **Поправка матовых счетов в TT корректна.** **[проверено]** round-trip
  `store` → `probe` сохраняет расстояние до мата на всех 50 комбинациях
  `ply_store` × `ply_probe` × знак. Клампы инертны, но безвредны.
* **Индексация history по цвету корректна.** **[проверено]** обновление идёт
  после `board.pop()`, поэтому `board.turn` — это сторона, сделавшая ход,
  и индекс совпадает с тем, который читает `_order_moves`. Для обоих цветов.
* **Стек доски сбалансирован.** Ни один ранний `return` не оставляет
  непарный `push`. **[проверено]** `board_intact=True` при обрывах по времени,
  при внешнем `stop()` из другого потока и при повторных вызовах на одном
  экземпляре движка.
* **Нелегальных ходов движок не возвращает.** Проверял отдельно, в том числе
  в тех самых случаях, где срабатывает откат C3: ход всегда легален,
  доска не портится. Пат в KQ vs K — это осознанный выбор движка, а не
  повреждение состояния.
* **Защита от цугцванга в null-move присутствует и верна** — `our_pieces`
  исключает пешки и королей.
* **Кламп LMR** `max(1, min(reduction, depth-2))` не даёт отрицательной глубины.
* **Индексация бонуса проходной пешки корректна** — `PASSED_PAWN_BONUS[r]`
  для белых и `[7-r]` для чёрных.
* **`MAX_PHASE = 6400`** точно соответствует стартовому не-пешечному материалу.
* **Модель потоков здравая.** `threading.Thread` + сверка `request_id`
  корректно отбрасывает устаревшие результаты.

   слишком широкий доверительный интервал для мелких правок.

6. **EPD-наборы** (WAC на тактику, STS на позиционное понимание) — быстрый

### Ещё два наблюдения из этих замеров

1. **На коротких бюджетах движок не выбирает своё время.** Правило
   `if elapsed > time_limit * 0.6: break` (`search.py:675`) прекращает углубление
   на 60 % бюджета, не оценивая, успеет ли следующая итерация. На 0.3 с реально
   тратится ≈ 0.19 с. Для пули это прямая потеря трети времени.
2. **`search_with_time_management` не используется в GUI** — там жёсткие 4.0 с
   (`main_window.py:33`). Если будете подключать часы, вот что даёт правило 5 %
   на первом ходу: пуля 1+0 → 3.0 с, пуля 2+1 → 6.8 с, блиц 3+0 → 9.0 с,
   блиц 3+2 → 10.6 с. Само по себе правило 1/20 самоограничивающееся и партию
   не проигрывает, но для пули стартовые 3 с на ход — слишком много,
   и пол `max(0.5, …)` в долгой партии всё-таки приведёт к флагу.
